## 0.状态管理概览

### 0.1 知识谱系

Flutter 的原生级的状态管理学习路线：
```
setState (理解重绘原理)
   │
   ▼
ValueNotifier + ValueListenableBuilder (局部精准刷新)
   │
   ▼
ChangeNotifier + ListenableBuilder (UI 与逻辑分离)
   │
   ▼
InheritedWidget / InheritedNotifier (跨页面/跨组件共享状态)
   │
   ▼
Notification + NotificationListener (自下往上的事件冒泡/逆向事件传递机制)
```

他们的状态管理机制的梳理：

  1. **`setState()`**：单组件内部的简单状态刷新（视图与逻辑混合）。
  2. **`ValueNotifier` + `ValueListenableBuilder`**：单变量精准局部刷新（轻量级解耦）。
  3. **`ChangeNotifier` + `ListenableBuilder`**：多变量 ViewModel 与 View 彻底解耦（MVVM 基础）。
  4. **`InheritedWidget`**：跨 Widget 树自上而下数据传递与 $O(1)$ 查找（依赖注入基石）。
  5. **`InheritedNotifier`**：ViewModel + 跨树依赖注入的终极组合，**无需父组件 `setState()` 即可驱动全局/区域状态精准更新**。

### 0.2 应用场景

#### 1. `setState()`

* **定位**：最简单的局部 UI 驱动。
* **业务场景**：
  * **开关与控制**：如单选框 `Checkbox` 选中、手电筒开关、密码框“显示/隐藏”切换。
  * **折叠展开**：手风琴列表（Accordion）项的展开/收起状态。
  * **动画辅助**：结合 `AnimationController` 在 `State` 内更新本地微交互状态。

* **反面教材**：**切忌将网络请求数据、全局用户信息或跨页面的 ViewModel 放在 `setState` 中**，会导致组件频繁重绘且难以维护。

---

#### 2. `ValueNotifier` + `ValueListenableBuilder`

* **定位**：轻量级单变量响应式刷新，追求极致性能与零样板代码。
* **业务场景**：
  * **表单提交按钮状态**：监听输入框字符长度，当密码 $\ge 6$ 位时自动高亮启用“提交”按钮（避免整个表单页面重绘）。
  * **输入字数统计**：评论框右下角的 `12/500` 字数实时变动。
  * **弹窗/遮罩显隐**：控制某个浮层或 Loading 指示器的显示与隐藏。

---

#### 3. `ChangeNotifier` + `ListenableBuilder`

* **定位**：单页面/单模块的 ViewModel，实现标准 MVVM 架构。
* **业务场景**：
  * **复杂表单页面**：例如“填写发票/寄件地址页”，包含姓名、电话、省市区三级联动选择、默认地址勾选等多个关联变量及校验逻辑。
  * **音频/视频播放器**：包含播放状态（播放/暂停）、缓冲进度、当前播放时长、音量大小等多个属性以及控制 API。
  * **倒计时组件**：带有开始、暂停、重置逻辑的验证码倒计时器。


---

#### 4. `InheritedWidget` / `InheritedNotifier`

* **定位**：跨层级依赖注入（DI）与状态共享，$O(1)$ 时间复杂度树内查找。
* **业务场景**：
  * **全局配置/主题**：App 深色模式/浅色模式切换 (`ThemeData`)、多语言国际化 (`Locale`)。
  * **全局/区域登录态**：当前登录用户的 `UserViewModel`，多处深层 Avatar 头像、VIP 标识、用户名展示组件实时同步。
  * **电商购物车/结算页**：购物车 ViewModel 挂载在购物页树顶层，深层商品列表卡片点击“+1”时，底部结算栏实时计算总价。


---

#### 5. `Notification` + `NotificationListener`

* **定位**：深层节点向外/向上通知事件（类似 DOM 事件冒泡），彻底杜绝层层传递 Callback。
* **业务场景**：
  * **列表滚动监听与联动**：监听 `ListView` 吐出的 `ScrollNotification`，实现悬浮 Header 吸顶、滚动过半出现“返回顶部”按钮、滑动到底部触发分页加载。
  * **深层卡片交互**：商品列表中，第 5 层嵌套的商品 Item 点击“加入购物车”或“分享”，不通过层层函数回调，直接 `dispatch` 一个 `AddToCartNotification`，由 Page 根节点统一捕获并弹出 Toast 或执行飞入动画。
  * **布局尺寸监控**：利用 `SizeChangedLayoutNotification` 动态捕捉子组件展开后的真实高宽并调整外层容器。

---

在拿到一个需求时，你可以按照以下逻辑来选择最恰当的原生机制：

```
                              需要管理状态/事件？
                                       │
            ┌──────────────────────────┴──────────────────────────┐
            ▼                                                     ▼
     跨层级组件通信？                                       单组件/单页面内部？
            │                                                     │
   ┌────────┴────────┐                                   ┌────────┴────────┐
   ▼                 ▼                                   ▼                 ▼
自上而下共享数据    自下而上冒泡事件                        多变量复杂业务逻辑   单变量/微更新
   │                 │                                   │                 │
   ▼                 ▼                                   ▼                 ▼
InheritedNotifier  Notification                     ChangeNotifier    ValueNotifier
                  (+NotificationListener)         (+ListenableBuilder) (+ValueListenableBuilder)
                                                                           │
                                                                   若仅为纯UI临时状态
                                                                           │
                                                                           ▼
                                                                      setState()

```


## 1.setState

### 1.1 基础介绍

`StatefulWidget` + `setState()` 是Flutter最基础的刷新机制。在 Flutter `中，Widget` 本身是**不可变的（Immutable）配置文件**，真实持有数据和生命周期的是其对应的 `State` 对象。调用 `setState()` 的**本质是**向引擎标记当前 `Element` 为 dirty（脏），促使框架在下一帧重新调用该 `State` 的 `build()` 方法，生成全新的 `Widget` 树进行 Diff 比对并更新渲染。


**注意⚠️：** 在发起网络请求、定时器或异步延迟操作时，如果在返回前用户退出了页面（组件已销毁/执行了 `dispose()`），此时调用 `setState()` 会抛出致命异常。正确做法先检查 `mounted` 属性：
```dart
Future<void> _fetchData() async {
  final result = await apiGetData();

  // 异步返回后，必须先判断组件是否还在 Element 树上
  if (!mounted) return;

  setState(() {
    _data = result;
  });
}
```

### 1.2 优化和注意点

#### 1.2.1 const优化

只要调用了 `setState()`，当前 `State` 的整个 `build()` 方法都会重新跑一遍。其内部没有加 `const` 关键字的子 `Widget`，**全都会重新实例化**。

* **优化策略**：
* **结构化拆分**：如果页面很长（如首页），不要在根页面 `StatefulWidget` 顶层调 `setState()`，把需要刷新的局部（如点赞按钮）抽离成独立的 `StatefulWidget`。
* **活用 `const`** ：对于不变的子 `Widget`（如纯文本、静态 Icon），加上 `const` 前缀，Flutter 会在重绘时自动复用已有的 `Element` 节点，跳过 `Rebuild`。


#### 1.2.2 严禁在 `setState()` 的闭包中写异步代码

`setState` 接收的回调必须是**纯同步函数**，不允许将闭包声明为 `async`。


```dart
// * **错误示范** ❌：
setState(() async {
  _data = await apiGetData(); // 编译报错或引发不可预期的更新逻辑
});

// * **正确示范** ✅：
final data = await apiGetData(); // 先拿完异步数据
if (mounted) {
  setState(() {
    _data = data; // 在 setState 中只做同步状态赋值
  });
}
```


#### 1.2.3 严禁在 `build()` 方法内部调用 `setState()`

在 `build()` 执行期间调用 `setState()` 会触发死循环（`build` -> `setState` -> 标记 dirty -> `build`），Flutter 会直接抛出 `Cannot update during build` 报错。所有的 `setState()` 必须由**用户手势交互（onTap）、事件订阅回调或 Timer** 等外部时机触发。


## 2.ValueNotifier

### 2.1 概念

`setState()` 中，最大的痛点是“牵一发而动全身”——只要调用 `setState()`，整个 `build()` 方法内部的所有 Widget 都会被重新构建。

`ValueNotifier<T>` 与 `ValueListenableBuilder<T>` 就是 Flutter 官方为了解决**细粒度（局部）刷新**而设计的原生组件。


**核心概念：它们是什么？**

* **`ValueNotifier<T>`（数据源 / 生产者）**：
继承自 `ChangeNotifier`，是一个包装了单个变量 `T` 的“监听器”。当它的 `.value` 发生变化时，它会自动通知所有订阅者。
* **`ValueListenableBuilder<T>`（视图 / 消费者）**：
一个特殊的 Widget。它专门订阅 `ValueNotifier`（或任何 `ValueListenable`）， **当数据变化时，只有这个 Widget 闭包内部的代码会重新 `build`** ，其外部的组件完全不受影响。

> **iOS 类比**：这非常类似于 Swift 中的 `@Published` 属性包装器配合 Combine，或者 KVO + 局部视图刷新的机制。

用法:
  - 1.定义并初始化 `ValueNotifier`
  - 2.使用 `ValueListenableBuilder` 订阅监听 `ValueNotifier` 的变化
  - 3.给 `ValueNotifier`的`.value`赋值，即可自动触发订阅的更新
  - 4.`ValueNotifier`必须在 `dispose()` 中销毁


**代码示例:**

```dart
// 代码在 _XxState 中
// 1. 定义并初始化 ValueNotifier
final ValueNotifier<int> _counter = ValueNotifier<int>(0);
final ValueNotifier<bool> _isLoading = ValueNotifier<bool>(false);

// build 函数
Widget _buildBody(BuildContext context) {
  // 观察控制台输出：无论点多少次按钮，这里只会在页面首次加载时打印一次！
  debugPrint("----------------- 页面根部 build() 执行了 -----------------");

  return Column(
    children: [
      // 静态不动的组件（绝对不会重复重绘）
      const Text(
        "假如这是一个渲染很重的静态标题",
        style: TextStyle(fontSize: 16, color: Colors.purple),
      ),
      const SizedBox(height: 20),

      // 2. 使用 ValueListenableBuilder 监听 _counter 的变化
      ValueListenableBuilder<int>(
        valueListenable: _counter,
        builder: (BuildContext context, int count, Widget? child) {
          // 只有这里的 builder 闭包在数据改变时会重新执行
          debugPrint(">>> 只有计数器 Text child = $child, count = $count");

          return Text(
            "当前计数器 $count",
            style: const TextStyle(fontSize: 25, fontWeight: FontWeight.bold),
          );
        },
      ),

      const SizedBox(height: 20),

      IconButton(
        onPressed: _increment,
        icon: const Icon(Icons.add, size: 40),  // 加号按钮
      ),

      const SizedBox(height: 50),

      // 4. 同理， 监听 _isLoading 状态
      ValueListenableBuilder<bool>(
        valueListenable: _isLoading,
        builder: (context, isLoading, _) {
          return isLoading
              ? const CircularProgressIndicator()
              : ElevatedButton(
                  onPressed: () async {
                    _isLoading.value = true;
                    await Future.delayed(const Duration(seconds: 4));
                    _isLoading.value = false;
                  },
                  child: const Text(
                    "点击模拟网络请求",
                    style: TextStyle(color: Colors.blue, fontSize: 20),
                  ),
                );
        },
      ),
    ],
  );
}

void _increment() {
  _counter.value++;  // 3. 直接给 .value 赋值即可自动触发更新
}
```

#### 2.1.2 核心优势

1. **极其优秀的 Rebuild 性能**：完全跳过了 `StatefulWidget` 的整树 Diff 比对，直接精准定位到具体的 Element 节点更新。
2. **甚至可以在 `StatelessWidget` 中使用**：如果 `ValueNotifier` 是从外部（如构造函数、全局变量或状态管理容器）传进来的，包含 `ValueListenableBuilder` 的页面本身可以是一个 `StatelessWidget`。

> ⚠️注意这点： `StatelessWidget`里面也是可以用 `ValueNotifier`的。

### 2.2 注意点

#### 2.2.1 集合类型（List/Map）修改内容不刷新的“深浅拷贝陷阱”
`ValueNotifier` 的内部 Setter 逻辑是判断 **`oldValue != newValue`** 才触发通知。
如果你使用的是集合，直接修改内部元素是**不会触发刷新**的：

```dart
final ValueNotifier<List<String>> listNotifier = ValueNotifier([]);

// ❌ 错误示范：列表地址没变，== 判断为 true，不会触发 UI 刷新！
listNotifier.value.add("新数据"); 

// ✅ 正确示范 1：重新赋值一个新的数组引用（浅拷贝）
listNotifier.value = [...listNotifier.value, "新数据"];

// ✅ 正确示范 2：或者继承 ValueNotifier 重新封装，手动调用 notifyListeners()
```

#### 2.2.2  记得在 `dispose()` 中释放资源

`ValueNotifier` 内部维护了一个订阅者列表。如果是在 `StatefulWidget` 中定义的 `ValueNotifier`，**务必在 `State` 的 `dispose()` 方法中调用 `notifier.dispose()**`，否则会导致 Listener 无法释放而产生内存泄漏。

#### 2.2.3 巧用 `ValueListenableBuilder` 的 `child` 性能优化参数

`ValueListenableBuilder` 的 `builder` 参数中第三个参数是 `Widget? child`。如果你有一个**非常庞大但不随数据变化**的子组件嵌在响应式区域内，可以提前传给 `child` 属性：

```dart
ValueListenableBuilder<int>(
  valueListenable: _counter,
  // 将不需要重绘的大组件传入 child
  child: const ExpensiveStaticWidget(), 
  builder: (context, count, child) {
    return Row(
      children: [
        Text('Count: $count'),
        child!, // 这里复用传入的 child，避免它跟着重复 build
      ],
    );
  },
);
```

#### 2.2.4 不要滥用：何时该升级到 `ChangeNotifier`？

* 当只需要控制 **单个简单变量**（如：`int` count、`bool` isLoading、`String` searchKey）时，`ValueNotifier` 是完美选择。
* 当业务逻辑变复杂，包含**多个互相依赖的变量**或复杂的方法计算时，应该升级到原生的 **`ChangeNotifier`** 将数据与方法统一封装到一个 Model 类中。


## 3.ChangeNotifier

**`ChangeNotifier` + `ListenableBuilder` 是 Flutter 原生实现“UI 与业务逻辑彻底解耦（MVVM 架构）”的标准工具。**

上面学习的`ValueNotifier`仅封装单一变量（通过 `.value` 读写），定位是轻量数据&局部刷新，但是对于复杂页面的多个变量和数据模型，并实现 MVVM 架构，就需要`ChangeNotifier`了。

**核心概念**

* **`ChangeNotifier`（ViewModel / 数据源）**：
继承自 `Listenable`。它是一个可以包含**多个属性和业务函数**的类。当属性发生变更时，通过显式调用 `notifyListeners()` 来通知所有的监听者。
* **`ListenableBuilder`（View / 监听器）**：
用于监听任意 `Listenable`（包括 `ChangeNotifier`、`ValueNotifier`、`Animation` 等），并在收到通知时**仅触发自身的 `builder` 重绘**。


**`ValueNotifier` vs `ChangeNotifier`**

| 对比维度 | `ValueNotifier<T>` | `ChangeNotifier` |
| --- | --- | --- |
| 状态维度 | 仅封装**单一变量**（通过 `.value` 读写） | 可封装**多个状态字段**及复杂计算逻辑 |
| 刷新触发 | 给 `.value` 赋值时**自动**触发 `notifyListeners()` | 需要在方法体内**手动**调用 `notifyListeners()` |
| 角色定位 | 纯数据包装器，用于轻量局部变量 | 标准 ViewModel，包含数据 + 业务处理逻辑 |
| 继承关系 | `ValueNotifier` 是 `ChangeNotifier` 的子类 | 原生基类 |

---

**解决的核心痛点**

1. **破解多变量管理混乱**：当一个页面有 `username`、`password`、`isLoading`、`errorMessage` 4 个状态时，用 `ValueNotifier` 需要定义 4 个对象并写 4 个 Builder；而用 `ChangeNotifier` 可以将其收拢在一个 ViewModel 中统一管理。
2. **真正实现 MVVM 架构**：把网络请求、校验逻辑、状态计算从 Widget 的 `build()` 中彻底剥离，Widget 变成纯粹的“受控组件”。

---


**代码示例：完整的购物车 ViewModel**

**1. 定义 ViewModel (Model 层)**

```dart
/// 1.定义 购物车 数据模型 model
class CartItem {
  final String id;
  final String name;
  final double price;
  int count;

  CartItem({required this.id, required this.name, required this.price, this.count = 1});
}

/// 2.继承 ChangeNotifier 充当 ViewModel，购物车 ViewModel
class CartViewModel extends ChangeNotifier {
  // 内部状态
  final List<CartItem> _items = [];
  bool _isCheckingOut = false;
  // 可以声明销毁状态标志，防止网络请求等异步之后，调用 notifyListeners() 产生异常。
  bool _isDisposed = false;

  // 对外暴露的只读属性与计算属性 List.unmodifiable(x) 返回不可变列表
  List<CartItem> get items => List.unmodifiable(_items);
  bool get isCheckingOut => _isCheckingOut;

  // 返回总价格
  double get totalPrice => _items.fold(0, (sum, item) => sum + (item.price * item.count));
  // 返回总数量
  int get totalCount => _items.fold(0, (sum, item) => sum + item.count);

  // 添加购物
  void addItem(CartItem item) {
    final index = _items.indexWhere((element) => element.id == item.id);
    if (index >= 0) {
      _items[index].count++;
    } else {
      _items.add(item);
    }
    // 修改数据后必须手动调用 notifyListeners()，才能让监听者知道
    notifyListeners(); // 通知视图刷新
  }

  // 移除指定 id 的商品
  void removeItem(String id) {
    _items.removeWhere((item) => item.id == id);
    notifyListeners(); // 通知视图刷新
  }

  // 提交订单，这里会模拟网络请求
  Future<void> checkout() async {
    _isCheckingOut = true;
    notifyListeners(); // 触发刷新展示 Loading  或者换成 _safeNotifyListeners();

    try {
      await Future.delayed(const Duration(seconds: 2)); // 模拟异步提交订单
      // 异步操作完成后，先检查是否已经被销毁
      if (_isDisposed) return;

      _items.clear();
      _isCheckingOut = false;
      notifyListeners(); // 结算完成，刷新 UI 或者换成 _safeNotifyListeners();
    } catch (e) {
      if (_isDisposed) return;
    }
  }

  /// 或者 封装一个安全的 notify 方法
  void _safeNotifyListeners() {
    if (!_isDisposed) {
      notifyListeners();
    }
  }

  @override
  void dispose() {
    _isDisposed = true;  // 在 dispose 时将标志位置为 true
    super.dispose();  // 可以在 ViewModel 中的 dispose释放资源，比如定时器之类的。
  }
}
```

**2. 视图层 (View 层)**

```dart
class CartPage extends StatefulWidget {
  const CartPage({super.key});

  @override
  State<CartPage> createState() => _CartPageState();
}

class _CartPageState extends State<CartPage> {
  // 实例化 ViewModel
  final CartViewModel _viewModel = CartViewModel();

  @override
  void dispose() {
    _viewModel.dispose(); // ⚠️务必销毁 ViewModel 释放内存
    super.dispose();
  }

    @override
  Widget build(BuildContext context) {
    // 省略 Scaffold(...) 样板代码，直接看 body 即可
  }

  Widget _buildBody(BuildContext context) {
    return Column(
      children: [
        // 1.商品显示区域
        Expanded(child: _buildCartItems(context)),
        // 2.底部结算区域
        _buildBottom(context),
      ],
    );
  }

  /// 购物车列表view
  Widget _buildCartItems(BuildContext context) {
    // 使用 ListenableBuilder 监听 ViewModel
    return ListenableBuilder(
      listenable: _viewModel,
      builder: (BuildContext context, Widget? child) {
        if (_viewModel.items.isEmpty) {
          return const Center(child: Text("购物车为空"));
        }
        return ListView.builder(
          itemCount: _viewModel.items.length,
          itemBuilder: (context, index) {
            final item = _viewModel.items[index];
            return ListTile(
              title: Text(item.name),
              subtitle: Text("单价: \$${item.price} x ${item.count}"),
              trailing: IconButton(
                icon: const Icon(Icons.delete),
                onPressed: () => _viewModel.removeItem(item.id), // 删除商品
              ),
            );
          },
        );
      },
    );
  }

  // 底部结算区域
  Widget _buildBottom(BuildContext context) {
    return Container(
      padding: const EdgeInsets.all(16),
      color: Colors.grey[200],
      child: ListenableBuilder(
        listenable: _viewModel,
        // 可以把完全不依赖 _viewModel 的静态组件传给 child 参数（会仅实例化一次）
        child: IconButton(
          onPressed: _onAddCart,
          color: Colors.blue,
          iconSize: 36,
          icon: Icon(Icons.add_shopping_cart),
        ),
        // staticChild 就是上面传进来的 IconButton 实例，可以在 builder 中直接复用
        builder: (context, staticChild) {
          return Row(
            children: [
              Text(
                '总计: \$${_viewModel.totalPrice.toStringAsFixed(2)}',
                style: const TextStyle(fontSize: 18,  fontWeight: FontWeight.bold),
              ),
              SizedBox(width: 12),
              _viewModel.isCheckingOut
                  ? const CircularProgressIndicator()
                  : ElevatedButton(
                      onPressed: _viewModel.items.isEmpty ? null : _viewModel.checkout,
                      child: const Text('结算'),
                    ),

              Expanded(child: SizedBox()),
              staticChild!, // 复用静态组件，跳过它的 Rebuild
            ],
          );
        },
      ),
    );
  }

  /// 添加购物
  void _onAddCart() {
    _viewModel.addItem(
      CartItem(
        id: DateTime.now().millisecondsSinceEpoch.toString(),
        name: '商品 ${getRandomInt(1, 100)}',
        price: 28.8,
      ),
    );
  }

  /// 生成一个指定范围内的随机整数，范围包含 min 和 max
  /// 例如：getRandomInt(1, 10) 会返回 1 到 10 之间的整数（包含 1 和 10）
  int getRandomInt(int min, int max) {
    final random = Random(); // 需要 import 'dart:math';
    return min + random.nextInt(max - min + 1);
  }
}
```


## 4.InheritedWidget

### 4.1 基础介绍

`InheritedWidget` 是 Flutter 官方提供的**沿 Widget 树自上而下高效共享数据**的底层组件。它是 `Theme.of(context)`、`MediaQuery.of(context)` 以及第三方状态管理库（如 `Provider`、`BlocProvider`）的底层基石。

---

**一、 它解决了什么问题？（核心优势）**

* **消除“构造函数透传”（Prop/Constructor Drilling）**：在没有 `InheritedWidget` 时，如果层级很深的第 10 层子节点需要第 1 层的数据，必须沿着第 2~9 层的构造函数逐层传递；`InheritedWidget` 允许任意深度的子组件通过 `context` 直接获取数据。
* **$O(1)$ 极速查找性能**：Flutter 的每一个 `Element` 内部都维护了一个指向祖先 `InheritedElement` 的哈希表（`Map<Type, InheritedElement>`）。因此，调用 `.of(context)` 获取数据时，不是向上递归遍历树，而是直接从当前 `Element` 的 Map 中读取，时间复杂度为 $O(1)$。
* **精确的依赖订阅与局部重绘**：当 `InheritedWidget` 的数据更新时，Flutter **仅会通知那些调用过 `.of(context)` 注册了依赖的子节点重绘**，中间没有调用 `.of(context)` 的层级完全不受影响。

---

在 Flutter 源码中，大量全局/区域配置共享功能均基于 `InheritedWidget`：

* `Theme.of(context)`：读取全局或局部的颜色、字号与主题样式。
* `MediaQuery.of(context)`：获取屏幕尺寸、设备方向、安全区域（Padding）和系统缩放。
* `Directionality.of(context)`：获取文本排版方向（LTR / RTL）。
* `DefaultTabController.of(context)`：在 TabBar 与 TabBarView 之间共享控制器状态。


> 因为`InheritedWidget`继承自`Widget`，是不可变的，适合仅充当静态数据传递者。

---

代码示例：
```dart
// 1.定义共享的数据实体
class UserConfig {
  final String username;
  final bool isDarkMode;
  const UserConfig({required this.username, required this.isDarkMode});
}

// 2.定义 InheritedWidget，需要继承抽象类 InheritedWidget
class UserConfigScope extends InheritedWidget {
  final UserConfig config;  // 这里是 final 的，因为 InheritedWidget继承自Widget，是不可变对象。

  const UserConfigScope({
    super.key,
    required this.config,
    required super.child,
  });

  // 2.1 提供静态 of 方法，方便子节点调用
  static UserConfig of(BuildContext context) {
    // dependOnInheritedWidgetOfExactType 会在当前 context 与该 InheritedWidget 之间建立订阅关系
    final UserConfigScope? scope = context
        .dependOnInheritedWidgetOfExactType<UserConfigScope>();
    assert(scope != null, '在当前的 BuildContext 上未找到 UserConfigScope');
    return scope!.config;
  }

  // 2.2 决定当外层重新 build 时，是否通知订阅了它的子节点重绘
  @override
  bool updateShouldNotify(UserConfigScope oldWidget) {
    return config != oldWidget.config;
  }
}

// 3.一般是挂载根，或者业务所需的地方
class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return UserConfigScope(
      config: const UserConfig(username: "Alex", isDarkMode: true),
      child: MaterialApp(
        home: const MainPage()
      ),
    );
  }
}

// 4.那么在任意深度的深层子组件中获取数据，无需构造函数传参
class DeepUserAvatar extends StatelessWidget {
  const DeepUserAvatar({super.key});

  @override
  Widget build(BuildContext context) {
    // 直接获取祖先节点数据，并自动建立依赖
    final config = UserConfigScope.of(context);

    return CircleAvatar(
      child: Text(config.username[0]),
    );
  }
}
```

### 4.2 查找机制的区别

在通过 `context` 获取 `InheritedWidget` 时，有两个名称相似的方法：

* **`context.dependOnInheritedWidgetOfExactType<T>()`**：
获取数据，并**建立依赖关联**。未来 `InheritedWidget` 更新时，当前 `context` 对应的 Widget **会重新 build**。
* **`context.getElementForInheritedWidgetOfExactType<T>()`**：
仅获取数据（或 Element 引用），**不建立依赖关联**。未来 `InheritedWidget` 更新时，当前 Widget **不会重绘**（常用于仅在点击事件回调中读取数据的场景）。

### 4.3 疑问解答

**1.`dependOnInheritedWidgetOfExactType` 怎么建立依赖的？**

在下面代码中：
```dart
static UserConfig of(BuildContext context) {
  // dependOnInheritedWidgetOfExactType 会在当前 context 与该 InheritedWidget 之间建立订阅关系
  final UserConfigScope? scope = context
      .dependOnInheritedWidgetOfExactType<UserConfigScope>();
  return scope!.config;
}

// 在某 Widget的 build 方法中使用：
final config = UserConfigScope.of(context);
return Text(config.username);
```

直觉上认为它“只是返回了一个变量”，但实际上这个方法在内部产生了一个极其重要的“副作用（Side Effect）”：**将当前页面注册到了祖先节点的订阅名单中**。


要理解这个机制，需要先明白：**`BuildContext context` 的本质就是 `Element` 对象。**

```
   【InheritedElement】
   - data: UserConfig
   - _dependents: [Element_A, Element_B] <-- 内部维护的“粉丝/订阅者名单”
            ▲
            │ 1. 注册订阅 (Side Effect)
            │
   【Element_A】(也就是你的 Child Widget 对应的 context)

```


#### 完整的 3 步“依赖建立与通知”流程：

**第一步：查找 + 隐式注册订阅（调用时）**

当写下这句话时：

```dart
final config = context.dependOnInheritedWidgetOfExactType<UserConfigScope>();

```

底层实际上执行了两件事：

1. **获取数据**：沿着 `Element` 树拿到 `UserConfigScope` 里的数据并返回。
2. **隐式注册（关键）**：`context`（即当前 Widget 的 `Element`）把自己的引用，**主动塞进了 `UserConfigScope` 对应的 `InheritedElement` 内部维护的 `_dependents`（订阅者集合）中**。

> **比喻**：你去前台拿报纸（获取数据），前台不仅把报纸给了你，还悄悄在她的记事本（`_dependents`）上写下了你的名字和房间号（注册订阅）

**第二步：数据发生变更（触发时）**

当 `UserConfigScope` 的数据更新（比如父组件 `setState` 重新传入了新的 `config`），并且 `updateShouldNotify` 返回 `true` 时。

**第三步：精准通知并重绘（响应时）**

`UserConfigScope` 对应的 `InheritedElement` 会取出记事本（`_dependents` 集合），遍历里面记录的所有 `Element`（比如 `Element_A`），对它们逐个调用：

```dart
element.markNeedsBuild(); // 标记为 dirty，通知 Flutter 在下一帧重新 build 这个 Widget

```

这就是为什么它不仅仅是“返回一个变量”，而是一个**带订阅副作用的注册动作**。只要你调过这个方法，你的 `context` 就被绑定到了那个 `InheritedWidget` 上，后续自动响应刷新。


----

**2.为什么 `UserConfigScope` 包在最外层就不会报错？**

`runApp(const Text("你好"))`运行会报错，但是`runApp(UserConfigScope())`不会报错是因为**组件是“向上”查找祖先节点的**，这时的结构如下：

```
Root (Flutter 根节点)
  └── UserConfigScope (最外层)
        └── MaterialApp  <-- 重点：它在内部注入了 Directionality、Theme、Navigator 等！
              └── ProfilePage
                    └── Text ("你好")
```

**结论**：`MaterialApp` 并不一定要作为 `runApp` 的绝对根节点，只要它处于所有 `Text` / UI 组件的上层（祖先节点）即可。`UserConfigScope` 放在 `MaterialApp` 外面，完全不影响 `MaterialApp` 向下为子节点提供 `Directionality`。


## 5.InheritedNotifier

### 5.1 InheritedWidget的痛点

上面的`InheritedWidget` 继承自 `Widget`，因此它的属性必须是 `final` 的不可变对象。它自己无法主动修改内部的数据。

传统的修改`InheritedWidget` 的方式是在它的**外层套一个 `StatefulWidget**`：

```
StatefulWidget (持有可变数据 state)
  └── CustomInheritedWidget (数据来自 parent 的 state)
        └── ChildWidgets
```

然后在合适的时机，调用`setState()`方法，`StatefulWidget` 则重新调用 `build()` 方法，就可以返回 `new` 一个新的`CustomInheritedWidget` 实例。

但是这种方式导致外层 Parent 被迫重绘，而且改变数据的逻辑依然写在 `State` 的 `setState()` 里，无法将数据逻辑彻底封装在独立的 `ViewModel` 中。

### 5.2 什么是InheritedNotifier

为了彻底解决上述痛点，Flutter 官方提供了一个继承自 `InheritedWidget` 的高级抽象类：**`InheritedNotifier<T Listenable extends>`**。

`InheritedNotifier` 相当于 **`InheritedWidget` + `Listenable` (如 `ChangeNotifier`) 的自动结合体**。

它接收一个 `notifier` 对象（比如你的 ViewModel），内部会自动向该 `notifier` 注册监听（`addListener`）。

```
        ViewModel (ChangeNotifier)  <--- 独立于 UI 之外的 ViewModel
                 │ (调用 notifyListeners)
                 ▼
    InheritedNotifier<ViewModel>    <--- 自动监听通知，无需父组件 setState()
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
  SubWidget A           SubWidget B  <--- 精准触发依赖子节点 Rebuild

```

> **一句话总结**：`InheritedNotifier` 让 `ChangeNotifier`（ViewModel）能够跨越 Widget 树传递，并且当 ViewModel 改变时，**无需父组件 `setState()`，深层子组件就能精准响应重绘**。这也是著名开源库 `Provider` 的底层核心思想。


代码示例：

**1. 定义 ViewModel (业务逻辑与状态)**

```dart
/// 1.定义 ViewModel，需要继承 ChangeNotifier
class UserViewModel extends ChangeNotifier {
  String _username = "Alex";
  bool _isPremium = false; // 是否是会员

  String get username => _username;
  bool get isPremium => _isPremium;

  // 更新用户名
  void updateUsername(String newName) {
    _username = newName;
    notifyListeners(); // 业务方法：改变状态后调用 notifyListeners(). 触发 InheritedNotifier
  }

  // 更新是否是会员
  void togglePremium() {
    _isPremium = !_isPremium;
    notifyListeners(); // 改变状态后调用 notifyListeners(). 触发 InheritedNotifier
  }
}
```

**2.定义 `InheritedNotifier` (跨层级注入容器)**

```dart
class UserScope extends InheritedNotifier<UserViewModel> {

  // 需要是 const修饰的构造函数
  const UserScope({
    super.key,
    required UserViewModel userViewModel,
    required super.child,
  }) : super(notifier: userViewModel);  // ⚠️注意要显式调用了父类的 super(notifier: userViewModel)

  // 或者使用 Dart(2.17+) 的最优雅写法
  const UserScope({
      super.key,
      required UserViewModel super.notifier, // 👈 直接用 super.notifier 接收并传给父类！
      required super.child,
    });


  // 1. 订阅获取（会触发 rebuild）
  static UserViewModel of(BuildContext context) {
    return context
        .dependOnInheritedWidgetOfExactType<UserScope>()!
        .notifier!;
  }

  // 2. 仅读取获取（不会建立依赖，不会触发 rebuild）
  static UserViewModel read(BuildContext context) {
    final element = context.getElementForInheritedWidgetOfExactType<UserScope>();
    assert(element != null, '在当前 BuildContext 及其祖先树中未找到 UserScope');
    
    final userScope = element!.widget as UserScope;
    return userScope.notifier!;
  }
}
```

## 6.Notification

### 6.1 概念

上面学习的`InheritedWidget` 和 `InheritedNotifier` 是 Flutter 状态管理中 **自上而下（Parent → Child）** 的数据传递和依赖注入机制。

而 **`Notification` + `NotificationListener`**，则是 Flutter 框架中对应 **自下而上（Child → Parent）** 的逆向事件传递机制。

对比 **自上而下 vs 自下而上**: 

```
【InheritedWidget / InheritedNotifier】      【Notification / NotificationListener】
           自上而下 (数据/状态共享)                      自下而上 (事件冒泡/通知)

            Parent Widget                              Parent Widget 
            (传递 State)                                (监听 NotificationListener)
                │                                           ▲
                ▼                                           │ (冒泡 bubble up)
            Child Widget                               Child Widget 
          (调用 of(context))                          (调用 dispatch(context))

```

* **`Notification`（通知）**：是一个抽象类，代表一个可以沿 Widget 树向上传播的**事件或信息载体**。
* **`NotificationListener<T>`（通知监听器）**：是一个 Widget，包裹在父节点外层，用于捕获指定类型 `T` 的 `Notification`。

---

### 6.2 它解决了什么问题？有哪些核心优势？

**1. 彻底规避 “Callback Drilling”（回调地狱 / 层层传递）**

* **传统做法**：如果树深层的 `LeafWidget` 发生了一个事件（如“用户点击了某种操作”），需要通知最外层的祖先 `ParentWidget`，传统方式必须在构造函数中一层层传递 `final VoidCallback onTap`。中间经过 5 层组件，5 层组件都要定义参数。
* **Notification 做法**：`LeafWidget` 直接发送通知 `dispatch(context)`，中间的 4 层组件**完全感知不到，也不需要传递任何回调**。外层的 `ParentWidget` 套一个 `NotificationListener` 即可直接捕获！

**2. 彻底解耦发送者与接收者**

* 发送通知的 Child Widget **完全不需要知道谁在监听它**，甚至不需要知道有没有人在监听。
* 接收 notification 的 Parent Widget 也不需要持有 Child Widget 的引用或 State。

**3. 支持“事件拦截与冒泡控制”**

* `NotificationListener` 的 `onNotification` 回调返回一个 `bool` 值：
* **返回 `true**`：阻止冒泡（Stop Bubbling），事件到此为止，更外层的祖先听不到。
* **返回 `false**`：允许继续冒泡，更外层的祖先也可以捕获该事件。


### 6.3 应用场景

1. **框架内置滚动监听（最常见）**：
  Flutter 的 `ListView`、`GridView`、`SingleChildScrollView` 等在滚动时，内部都会自动向外 `dispatch` **`ScrollNotification`**（如 `ScrollStartNotification`, `ScrollUpdateNotification`, `ScrollEndNotification`）。你可以在不传入 `ScrollController` 的情况下，用 `NotificationListener<ScrollNotification>` 直接监听滚动状态。
2. **深层子组件向外透传业务事件**：
  例如嵌套表单重置、深层卡片拖拽交互、埋点日志事件收集等。
3. **布局/尺寸变化通知**：
  Flutter 内置的 `SizeChangedLayoutNotification`，子组件尺寸变化时向外通知。

---

自定义 `Notification` 实现跨层级事件冒泡步骤：
  - 1.自定义类实现`Notification`，例如`class MyNotification extends Notification`
  - 2.在根页面使用 `NotificationListener` 捕获通知。例如 `child: NotificationListener<MyNotification>{ return true/false }`
  - 3.在子组件中，主动发送通知`MyNotification('数据').dispatch(context);`


### 6.4 代码示例

#### 示例 1：使用内置的 `ScrollNotification` 监听列表滚动

在无需定义 `ScrollController` 的情况下，精准捕获列表的滚动进度与状态：

```dart
class ScrollNotificationDemo extends StatefulWidget {
  const ScrollNotificationDemo({super.key});

  @override
  State<ScrollNotificationDemo> createState() => _ScrollNotificationDemoState();
}

class _ScrollNotificationDemoState extends State<ScrollNotificationDemo> {
  String _scrollStatus = "静止";
  double _progress = 0.0;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('滚动进度: ${(_progress * 100).toInt()}% ($_scrollStatus)')),
      // 1. 包裹 NotificationListener，指定监听 ScrollNotification 类型
      body: NotificationListener<ScrollNotification>(
        onNotification: (ScrollNotification notification) {
          // 2. 根据 notification 的具体子类型判断状态
          if (notification is ScrollStartNotification) {
            setState(() => _scrollStatus = "开始滚动");
          } else if (notification is ScrollUpdateNotification) {
            // 计算当前滚动百分比
            final metrics = notification.metrics;
            setState(() {
              _scrollStatus = "滚动中";
              _progress = (metrics.pixels / metrics.maxScrollExtent).clamp(0.0, 1.0);
            });
          } else if (notification is ScrollEndNotification) {
            setState(() => _scrollStatus = "停止滚动");
          }

          // 返回 false 允许事件继续向上冒泡；如果返回 true，更外层的 NotificationListener 将收不到此通知
          return false;
        },
        child: ListView.builder(
          itemCount: 50,
          itemBuilder: (context, index) => ListTile(title: Text('Item $index')),
        ),
      ),
    );
  }
}

```

#### 示例 2：自定义 Notification 实现跨层级事件冒泡

假设我们有一个跨越多层节点的深层按钮，希望点击时通知顶层的页面：

```dart
import 'package:flutter/material.dart';

// 1. 自定义 Notification，继承自 Notification 类
class CustomLogNotification extends Notification {
  final String message;
  final DateTime timestamp;

  CustomLogNotification(this.message) : timestamp = DateTime.now();
}

// 2. 根页面：监听深层冒泡上来的通知
class CustomNotificationDemo extends StatefulWidget {
  const CustomNotificationDemo({super.key});

  @override
  State<CustomNotificationDemo> createState() => _CustomNotificationDemoState();
}

class _CustomNotificationDemoState extends State<CustomNotificationDemo> {
  final List<String> _logs = [];

  @override

          });

        },

            const MiddleLevelWidget(),
          ],
        ),
      ),
    );
  }
}
```

### 6.5 原理速览：`dispatch(context)` 底层是怎么运行的？

`Notification.dispatch(BuildContext? context)` 的源码逻辑非常简单精妙：

```dart
void dispatch(BuildContext? target) {
  if (target == null) return;
  
  // 1. 获取当前节点对应的 Element
  Element? element = target as Element?;
  
  // 2. 沿着 Element 树向上遍历祖先节点 (visitAncestorElements)
  while (element != null) {
    if (element is StatefulElement && element.state is _NotificationListenerState) {
      // 3. 如果祖先是 NotificationListener，调用其 handleNotification 方法
      final _NotificationListenerState listener = element.state as _NotificationListenerState;
      if (listener.handleNotification(this)) {
        // 4. 如果 onNotification 返回 true，中断循环，停止冒泡！
        break;
      }
    }
    // 继续往上一层祖先遍历
    element = element.visitAncestorElements(...) ? ... : null;
  }
}

```

**时间复杂度**：只遍历当前 Widget 的祖先链，复杂度为 $O(d)$（$d$ 为树的深度，通常小于 30），因此执行极其高效。

### 6.6 三大原生机制对比总结

| 维度 | `InheritedWidget` / `InheritedNotifier` | `Notification` / `NotificationListener` | 普通 Callback (`void Function()`) |
| --- | --- | --- | --- |
| **传递方向** | **自上而下** (Parent → Child) | **自下而上** (Child → Parent) | 双向（需在构造函数显式传递） |
| **耦合度** | 低（通过 BuildContext 向上查找） | **极低**（仅触发派发，无关联） | 高（中间所有层级都需要声明参数） |
| **主要功能** | 共享数据、依赖注入、驱动 UI 重绘 | 传递操作事件、阻断冒泡、状态监控 | 单一对一的直接通信 |
| **重绘范围** | 仅依赖该 InheritedWidget 的子节点 | **不自动触发重绘**，需在 Listener 中配合 `setState` | 取决于回调接收方是否 `setState` |
